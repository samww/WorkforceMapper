# WorkforceMapper

An ASP.NET Core + React application for workforce capacity maintenance, with an AI layer for natural language capacity and risk reporting.

Pre-loaded with 80 resources (employees, contractors, and vendor staff across 4 divisions) mapped to 48 activities across 18 applications and 12 projects — ready to query immediately across all 12 months of 2026.

Companion project to [product-portfolio-rag](https://github.com/samww/product-portfolio-rag): both use the same fictional company (Pragmenta Insights). The workforce allocations here are the operational source behind the application cost figures in that project.

## What it does

**Mapping UI** — per-resource cards with inline allocation editing. Division filter, unallocated filter, over-allocation highlighted in red. Percent values are positive integers (1–100); the API hard-caps each resource at 100% per month.

**Applications view** — lists all 18 applications with capacity coverage, risk classification (high / medium / low relative to `min_support_fte` / `recommended_support_fte`), and dependent products. Includes a dependency graph rendered via Mermaid.

**Products view** — 7 products with aggregated ARR ($28.9m total), product risk (max-wins over transitive application dependencies), and contributing applications per division.

**Projects view** — 12 projects with FTE allocation across their activities.

**Natural language queries** — ask plain English questions over the mapped data. Claude calls structured tools to retrieve capacity, cost, product attribution, run/change split, application risk, and donor candidates — no freeform SQL.

## Data model

```
resources ──< mappings >── activities ──> applications ──< product_applications >── products
                                     └──> projects     ──< project_products     >── products
                                          applications ──< application_dependencies >── applications
```

- **80 resources** across 4 divisions: Platform Engineering (23), Analytics (24), Data Collection (20), Client Services (13)
- **48 activities** — each belongs to one application (Support + Minor Changes) or one project (Project type); prefixed P01–P12 for projects
- **3,144 mappings** covering all 12 months of 2026; generated by `scripts/generator.ts`
- **18 applications** with support thresholds; **12 projects**; **7 products** — all 7 transitively depend on AuthService

Default month: **2026-05** (UI has a month dropdown).

## Demo auth toggle

Two `workflow_dispatch` workflows in the Actions tab let the maintainer flip Easy Auth on and off during live demos:

- **Demo - disable auth (allow anonymous)** — sets the unauthenticated-client action to `AllowAnonymous` so attendees can open the app URL without an Entra sign-in prompt.
- **Demo - enable auth (require sign-in)** — restores `RedirectToLoginPage`.

Note: "off" is `AllowAnonymous`, not a full disable — Easy Auth and the Entra app registration remain configured throughout. Signed-in users continue to receive `X-MS-CLIENT-PRINCIPAL` headers.

One-time setup: run `scripts/setup_demo_auth_toggle.ps1` to create the OIDC service principal and add the required GitHub Secrets (`AZURE_CLIENT_ID`, `AZURE_TENANT_ID`, `AZURE_SUBSCRIPTION_ID`).
